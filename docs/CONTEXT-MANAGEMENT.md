# 上下文管理

假设你让 BearCoding 修复 `App.java`。你以前说过「别改包名」，这次第一次跑测试又返回了一份很长的失败报告。后端每次叫模型继续工作，都要送过去一包材料，包括需求、规则、旧聊天、工具说明和已经拿到的结果。材料太多，后端会整理这次发送的副本。模型发现缺了旧信息，可以主动查回。

## 旧材料放在哪里

| 材料 | 放在哪里 | 需要时怎么找 |
|---|---|---|
| 你说过的「别改包名」、助手以前的回复 | 会话数据库的 `conversation_message` 表 | 用 `searchContext`（查旧上下文）搜原文关键词，或按消息编号读取 |
| 第一次测试的长报告 | 满足条件且保存成功时，后端把这次捕获的工具输出文本另存为临时文件，称为「落盘快照」 | 用 `readFile`（读文件）传入那次结果留下的签名引用，按行读取 |
| 本次任务拿到的材料 | 源账本（`ContextSourceLedger`），本次请求内的材料登记表 | 用于每轮打包。工具交来的是预览和引用时，账本登记的也是预览和引用 |
| 工具审计记录 | `tool_call_log`，用于查看调用经过，结果正文最多保留约 4000 字符 | 查调用经过。全文恢复走快照入口 |

## 一次任务里，后端何时整理材料

1. **开工前看旧聊天。** 默认配置下，后端读出当前会话历史，有条件地请模型把够早的一段聊天写成摘要。近期对话和你这一次刚发的要求在这一步按原文加入材料。
2. **每轮发送前做副本。** 模型想跑测试，后端执行工具并收到结果；准备下一次调用模型时，后端按本轮条件挑选材料。这份准备发送的副本叫「工作集」。把一条旧材料的正文换成简短提示，项目里叫「退休」。能退的内容当轮就少发，下一轮再按当时条件重新判断。
3. **检查后发送。** 调用和结果要对得上，整包材料要装得进所选模型的窗口，这一次调用还要有足够的任务累计额度。
4. **缺哪份就查哪份。** 模型可以按需请求查找，后端负责核对归属、引用和权限，返回对应内容。模型需要先察觉自己少了哪条信息。

举例来说，后端可能用一段短摘要代替很早的聊天，同时把第一次失败报告的预览换成取件条。你当时说的原话仍在数据库，报告仍取决于对应的快照文件。重新跑测试得到的是当前代码的结果。

## 历史摘要

默认开启工作集，压缩范围为 `history`。后端在一条用户请求进入工具循环前检查一次。它先看**此前的聊天正文**有没有超过触发线，模型窗口为 128000 时，默认触发线是 83200（65%）。如果有可用的旧摘要，也可以直接复用。

需要新摘要时，后端从最早的聊天开始选连续的一段。最近 **3 个历史用户回合**和本次请求不参与摘要。候选段只收录有数据库编号、正文非空的用户消息和助手回复，遇到其他记录就停在前面。尚未覆盖的候选内容估算至少要有 1200 token。Token 是模型计算文本用量的单位。

模型负责写摘要。后端检查结果非空、长度合格（摘要正文最多 4000 字符），以及加上说明之后确实缩短了历史材料。采用的摘要会标明覆盖的消息编号，例如 `message|101` 到 `message|160`。后端保留数据库原话，并在打包时跳过被摘要覆盖的旧正文。模型可能漏掉「别改包名」这类关键要求，后端检查摘要的格式和大小，可靠的原话仍要按消息编号查回。

摘要暂存在运行中的程序内存里，按用户和会话区分，最多记住 64 个会话，优先淘汰最久没用的那份。同一段原话没变时可以直接复用。如果要扩大覆盖范围，只把「上一版摘要 + 新变旧的聊天」交给模型。覆盖内的原话变化时会让原摘要失效。同一范围失败过或没有缩短材料，程序会记下这次尝试，范围没扩大前暂缓重试。重启或换实例后，后续请求可以在满足条件时从原话重新生成摘要。

首次摘要失败时，保留原历史进入后续整理。已有有效摘要时，增量更新失败就继续用上一版，新增但还没覆盖的消息保留原文。最终材料仍超出单次模型窗口时，后端会拦住那次主模型调用。标签如 `applied`（采用）、`reused`（复用）、`calls`（本次摘要尝试数）和前后估算可以在日志中帮助排查。复用摘要本身没有额外的摘要模型调用。即使模型返回的摘要最终被舍弃，已发生的调用仍可能有成本。

## 工作集怎样少发旧材料

默认开启工作集。每轮打包时，后端留住当前用户要求、系统规则、正在执行的计划、近期内容和能识别出仍被计划使用的证据。较老的助手回复符合规则时，可以换成带消息编号的一行提示。

以第一次测试的报告为例，工作集要在本轮少发它，需要同时满足这些条件：

1. 当前候选材料中的历史正文与工具结果正文相加，估算超过工作集软线。默认是 64000。
2. 这是本次任务里至少三个模型轮次前的结果。按主代理的工具循环计算轮次。刚读回的结果还有下文的六轮保护。
3. 如果结果被关联到一个计划步骤，该步骤已经完成。普通未关联的结果也可以参照其他条件判断。
4. 同一批调用的每一项都有对应结果，并通过快照检查。结果要带有效签名引用，快照在此刻可读且内容一致。

条件满足时，本轮副本保留工具调用和对应的结果编号，只把结果正文换成「已省略，凭取件条读取」。校验失败时保留手上已有的内容，可能是一段预览。超过软线以后能少发多少，取决于这轮有多少材料符合条件。旧助手回复的软线规则单独看这条回复之后的历史正文。

**消息配对**可以理解成核对单号。第 7 号测试调用要有第 7 号结果，保留原编号的省略说明也能对上。这个检查只核对调用和结果的编号与顺序。工作集副本配对失败时，后端回退到整理前的发送材料。最后选用的材料配对正确且符合窗口和预算，才会发出。

## 工具快照何时还能读回

快照保存的是某一次工具实际捕获的文本。如果修改 `App.java` 后再跑一次测试，且新的长输出也成功落盘，两次报告分属各自的快照文件。直接改动旧报告文件会导致内容指纹对不上，旧引用的读取会失败。

后端在退休前和真正读取时都检查取件条的签名、当前会话的读取权限、文件是否存在及内容指纹。指纹用 SHA-256（按文件字节计算的校验值）。读取用的是刚刚通过校验的那份数据。签名引用失效、文件被清理、权限不符或指纹不一致时，会返回原因，模型可以据此说明情况。需要拿到当前状态时，可以重新执行原工具。

- **文件的临时保护。** 采用退休引用准备本轮副本时，后端给快照登记约 1 小时的进程内保护。常规按年龄或容量清理会跳过保护中的文件，重启后这项登记消失。默认的 24 小时是启动清理的文件年龄条件。后续请求有时还能读取仍存在的快照，前提是拿得到有效引用并通过当前权限检查。此前的工具结果不会自动从快照文件重新装入聊天。
- **读回结果的短期保护。** 通过签名引用或 `searchContext` 的读取操作取回内容后，这条新的工具结果在本次任务的 6 个模型轮次保护期内暂不退休。保护期过后，重新按普通退休条件判断。

[MCP 长结果的保存规则](MCP-AND-SECURITY.md)也适用这套取件条思路。子代理的单条工具结果另有字符限制，默认 4000；主循环的 12000 字符限制只在启用 `app.subagent.dispatch-v2` 时使用，该开关默认关闭。

## searchContext 怎样找回原话

知道消息编号时，比如 `message|120`，用 `operation=read` 直接按号读取。只记得「包名」时，用 `operation=search` 查候选片段，再按返回的定位编号读取。旧聊天目前由数据库做原文包含匹配，多个关键词可任一命中，结果按消息编号排序。搜索可继续翻页，长消息也可分段读取。

`searchContext` 是默认允许的只读工具。后端从当前登录用户和会话确定范围，可查本会话消息、该用户的记忆和当前计划。**工具快照走 `readFile` 的签名引用入口**。因此搜不到第一次测试报告时，要辨认手上缺的是一句旧聊天，还是某次工具实际返回的结果。

## 两种记忆

| | 工作区记忆 | 用户记忆 |
|---|---|---|
| 用来记什么 | 项目约定，例如「修改后跑一次启动检查」 | 用户偏好，例如「讲 Java 先举例子」 |
| 保存和使用 | 用 `saveMemory` 写到当前工作区的 `memory/*.md`，同工作区对话时按限额加入材料 | 用 `saveUserMemory` 或 `forgetUserMemory` 修改本地数据库中的用户记录，该用户之后的主对话可用，默认上限 40 条 |
| 权限 | 按内置工具规则 | 保存和删除每次审批，完全访问档也要确认 |

两类记忆默认开启，子代理不自动收到这两份主对话材料。用户记忆写入会检查一部分明显的凭证格式。记忆内容是否确实出自用户这轮的明确表达，由模型按提示要求判断，后端负责审核交互与写入。

## 配置与验证范围

### 几条预算各管什么

| 配置 | 默认 | 用途 |
|---|---:|---|
| 所选模型的 `contextWindowTokens` | 未配时按 128000 估算 | 每次发送前检查整包输入。该回退值只是 BearCoding 使用的估算窗口 |
| `app.context.compact-window-percent` | 65 | 默认在开工前比较此前的聊天正文与模型窗口的 65%，超过这条线才考虑新摘要 |
| `app.context.working-set.soft-budget-tokens` | 64000 | 每轮打包时判断历史和工具结果的估算量是否已经有压力，超过后旧工具结果才有机会退休 |
| `app.context.history-max-tokens` | 64000 | 旧历史整理路径里近期原文的保留目标，也是窗口未知时的备用触发线。默认历史摘要路径按最近用户回合及可摘要范围选内容 |
| `app.context.task-input-token-budget` | 2000000 | 一次用户请求里各次模型调用的累计输入额度，连同额外摘要等调用一起计入。同一材料重复发送也重复计入。下一次估算放不进剩余额度时会被拦住，设为 0 可关闭这条限额 |

累计额度先按发送前的估算记账。服务商回报的输入量高于估算时，再补记差额。旧的 `app.context.max-tokens` 仍留作回退配置，优先使用 `history-max-tokens`。外部工具说明是否按需加载，用 [MCP 的独立参考窗口](MCP-AND-SECURITY.md)判断。

`working-set.shadow-enabled` 默认开启。关闭实际工作集、单开这项时，工作集仍试算分类，但不会把试算结果应用到发送材料。开启工作集时也会留下对照日志，包括估算量、退休量和保留原因。

默认开工前的历史摘要走 `ContextCompactor.assemble`，满足条件才调用模型。关闭工作集且仍用 `history` 时，走另一套按历史预算整理的 `buildMessages`。非默认的 `total` 会在循环里看整包输入。关闭工作集时，`compact-strategy` 可选择 `summary`（用模型概括）、`digest`（按规则截短或用占位符，异常时可能退到摘要）或 `tiered`（先按规则缩短，缩短后仍高于整理触发线的 90% 时再试摘要，比例可配）。工作集开启且使用 `total` 时，循环中额外的副本整理固定走 `digest`，不增加模型摘要调用。

### 验收记录怎么看

[真实模型验收](../evidence/bearcoding-final-f1-f2-fix-and-context-acceptance-20261114.md)记录了默认配置下生成历史摘要后按编号找回旧原话，也记录了临时将工作集软线降到 5000 后，工具结果退休并按签名引用读回。默认 64000 的那组工具结果试验没有到达退休条件。

这些记录证明对应流程在那些任务里走通过。整理减少的是之后发送的材料，已经跑过的工具不因此少跑。日志里的 token 估算和测试替身给出的模拟用量都不是账单，仓库也没有相同任务开关前后的真实费用对照。摘要质量和模型能否主动找回线索，仍需要看具体任务。

## 旧聊天混合检索设想（尚未实现）

这里的混合检索指的是**让同一次搜索同时查旧消息原文和另存的主题词**。比如旧聊天写的是「留下原来的包声明」，本次模型却搜「包名约束」。给旧消息补上「Java 包名、修改约束」这样的主题词，有机会让它进入候选。直接搜 `App.java`、错误码或原句时，原文匹配仍能提供线索。

1. **让主题词只帮忙找候选。** 可为部分旧消息生成少量主题词，并关联到原消息编号。同一次查询把原文命中和主题词命中合并，按编号去重，返回少量候选。给明确的原文命中保留位置，避免通用标签抢占结果。候选保留消息编号、实际原文片段和命中来源，确认细节仍按编号读原话。原文改动或删除时，对应的主题词也应失效。
2. **排序和摘要分开验证。** 第一版可以继续用现有的原文匹配，先验证多一条主题词入口有没有帮助。后面再考虑用 BM25（根据关键词匹配程度排序的算法）改进候选排序，尤其要分别验证中文短词和代码标识符。另外可以实验对**反复被有效读回**的单条消息只生成一次短摘要，例如把三次当作试验门槛。要先定义何为有效读回，排除同一段被空转重复读取。短摘要仍是辅助材料，与现在按一段旧对话生成的历史摘要分开。
3. **用同一组问题做对比。** 先记录现有原文检索结果，再对照加入主题词后的结果。覆盖原句、代码标识符、换一种说法、多个相似主题等场景。看正确原文能否进前几条、是否挤掉原先能找到的精确结果、模型能否选对编号，以及生成主题词和摘要带来的额外时间、输入和费用。

改进范围先限定为当前会话的旧聊天，沿用归属检查和按编号读原文。主题词可能标错或漏标，后端能提供更多可查线索，模型仍需要知道何时去查、查到后读哪条。工具快照继续按签名引用读取。关键词加向量相似度属于可另行评估的方向。

公开实践可作设计参考。RAGFlow 公开了让模型为文档片段提取关键词以辅助检索的做法。OpenClaw 公开了关键词与向量相似度结合的记忆检索。它们分别与这个设想有相似点，具体实现与结果仍要在 BearCoding 上单独验证。 [RAGFlow 文档](https://ragflow.io/docs/v1.0.0/configure_transformer_component) · [OpenClaw 文档](https://docs.openclaw.ai/concepts/memory-builtin)
