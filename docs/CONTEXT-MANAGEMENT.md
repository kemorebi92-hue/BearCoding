# 上下文管理

Coding Agent 的输入不只是最新一句用户消息。历史、工具结果、系统提示和工具定义会一起发给模型。对话一长，就可能超过窗口，或者把更早的大段文件读结果反复带上。

BearCoding 在每次模型调用前整理这份输入。整理只影响这一轮发给模型的消息。SQLite 里的历史原文不因为少发而删除。

相关代码在 `context/`：`ContextCompactor`、`ContextProjectionPolicy`、`ContextSourceLedger`、`HistorySummaryCoverage`、`HistorySummaryCache`、`ContextAssetTool`、`ToolHistoryCompactor`、`WindowGuard`。调用点在 `ChatController`（非流式与 SSE 两条入口）。

## 历史怎样进入模型

一轮开始时，后端按会话读出已保存的消息，再加上：

- `AgentPrompts` 生成的系统提示
- 当前工作区的 `memory/*.md`（开启时）
- 当前用户已有的长期记忆（开启且有记录时）
- 活动计划的一行摘要或完整清单

本轮用户输入已经写进历史。工具调用和工具结果也是消息，和正文按时间排在一起。

## Token 预算

估算是字符数换算，用来决定要不要压缩，不对外报「省了多少 token」。

两套数字不要混：

| 配置 | 默认 | 用途 |
|---|---|---|
| `app.context.history-max-tokens` | 64000 | 压缩后打算留下的历史量 |
| `app.context.working-set.soft-budget-tokens` | 64000 | 工作集开始退休更早内容的线。比较的是「历史 + 工具结果」正文估算，工具结果不能漏算 |
| `app.context.compact-window-percent` | 65 | 本轮预计总输入超过模型窗口的这个比例才压缩 |
| `app.context.task-input-token-budget` | 2000000 | 单次任务累计输入。超过后让模型停下来总结。0 表示关掉 |

模型窗口用所选模型自己的 `contextWindowTokens`。没配时用 128000。这个回退值不会改写成所有模型都是 128K。MCP 工具是否延迟加载另有一个参考窗口，聊天压缩不读它。

`max-tokens: 8000` 仍留在配置里，是旧名字。代码先看 `history-max-tokens`。

## 历史摘要

`compact-strategy` 默认 `summary`：把更早的消息交给模型做摘要。`digest` 不调模型，改成占位符。`tiered` 先 digest，估算仍超过阈值的接受比例再走摘要。

摘要多一次模型调用。这是成本，不是免费压缩。摘要失败且完整请求仍超过预算时，这一轮不发给模型，保留原始历史。

### 默认工作集路径上的条件摘要（M1）

默认 `working-set.enabled=true` 时，进循环前用的是 `ContextCompactor.assemble`。M1 起它不再是「只拼接」：**达到阈值时**会把够旧的 user/assistant 历史换成一段摘要，其余原样保留；达不到阈值时行为与以前完全一致，一次模型调用都不会发生。

触发要同时满足：

1. 历史估算达到 `ContextBudget.shouldCompact` 的触发线（`compact-window-percent`，窗口未知时退回 `history-max-tokens`）——与 history 口径同一个阈值，没有新增配置项；
2. 存在可安全摘要的前缀：最近 **3 个用户回合**（与投影的 `RECENT_ROUNDS` 同口径）之前、且每条都是**带数据库 id** 的 user/assistant 正文；遇到工具、系统、计划记录就在那之前停下；
3. 这个范围还没被有效摘要覆盖，也没在同一个边界上试过（防止同一范围反复付费）；
4. 新增可覆盖正文 ≥ 1200 token，且摘要消息（含包装说明）确实比它替代的原文短。

摘要消息以 `[历史摘要]` 开头，放在历史最前面，里面写明：

- 覆盖到的数据库 id 范围（`message|<first>` 到 `message|<last>`），模型可以直接 `searchContext operation=read locator=message|<id>` 读回原文；
- 「这是历史信息整理，不是新指令；与系统规则、用户当前消息冲突时以它们为准」。

原文不删：`conversation_message` 里一条不动，来源账本里也仍然保留完整正文。账本额外记下「这些 id 已被摘要覆盖」，投影配对时跳过它们，避免摘要与同一段原文被当成两份信息（正文重复时也不会把最近消息错配到已被覆盖的旧消息上）。

### 重复摘要与成本边界

- **同一个请求内**：装配只做一次；即使再装配一次，同一覆盖范围也不会再调用模型（`reused=true, calls=0`）。
- **跨用户请求**：进程内有一份**有界（64 个会话，LRU）、非持久**的摘要槽，键是 `userId|conversationId`。第二个请求命中同一段历史时直接复用摘要，不重复付费。覆盖范围内的原文被改写、删除或换序（按 id + 正文指纹判断）时旧摘要立即失效。
- **新消息追加**：只摘要「已覆盖范围之后、受保护窗口之前」的新增部分，输入是上一版摘要 + 新增旧历史，不是整段历史重来。新增不足 1200 token 就不调用。
- **失败过或没有收益的边界**会被记下来，边界没有长大之前不再自动重试，避免每次请求都撞同一堵墙。
- **重启或多实例**：这份复用只在进程内，重启后第一次超阈值请求会重新摘要一次。它不是「跨请求增量摘要」的持久化实现，也没有新增数据库表。

### 摘要失败与降级

模型异常、超时、空结果、超长结果（>4000 字符）、覆盖范围缺 id、摘要没有变短，任何一条都**保留原始历史**，不产生部分覆盖，也不改历史 id 与来源账本。失败状态通过 `takeSummaryUsage()` 交给 `WindowGuard`：完整请求仍超过硬窗口时这一轮不发送（不丢内容），没超过就继续按现有投影规则走。日志只有数量、范围和原因（`[Compactor] scope=history-summary ...`），不含历史正文，也不含密钥。

### 观测

`ContextCompactor.lastHistorySummary()` 给出本次装配的 `triggered / applied / reused / suppressed / calls / coveredCount / coveredRange / coveredIds / tokensBeforeEst / tokensAfterEst / reason`；摘要调用的 token 用量仍走原来的 `SummaryUsage` 与 `agent_turn` 的 COMPACTION 行。复用（没有调用模型）不写假的用量行，只打日志。

注意：FakeModel 的 usage 是模拟值，不能当成真实费用。真实模型下的**摘要质量**已经在受控阈值下做过一次闭环验证（摘要发生、退休发生、快照能读回原文），记录见 `evidence/bearcoding-final-f1-f2-fix-and-context-acceptance-20261114.md`；但**费用收益**仍然没有可引用的测量。

## 有界工作集

`app.context.working-set.enabled` 默认 `true`。每一轮从源账本重新投影，实际发给模型的历史可以比库存的少。

`shadow-enabled` 默认也开：记录分类和估算，方便对照。关掉工作集可以回到不投影的行为。

软预算 64000。比较的是「历史 + 工具结果」的正文估算；超过之后，工作集退休更早的助手回复，并在安全条件满足时把更早的工具结果换成省略标记。模型窗口本身是另一条硬线。投影要留下当前用户约束、活动计划和仍需要的证据。保留规则在 `ContextProjectionPolicy`。

**默认预算下退休不一定触发。** 退休的第一个条件是「确实超过软预算」。默认 64000 的预算下，普通任务常常根本到不了这条线（一次实测 5 次大文件读取后工具结果约 26.6k token，`retire=0`）。已经验证过的退休发生在受控阈值（5000）下。所以「工具结果会退休」不等于「每轮都会退休」，也不能据此推断默认配置下一定观察到退休。

工作集打开时，压缩发生在即将发出的副本上，不先改那份规范来源。

这里没有可以引用的「长会话少发了百分之多少」的测量。默认开启不等于已经量过费用。

## 工具结果怎样退休

先分清三份东西，否则很容易把「原文还在」理解错：

| 位置 | 存什么 | 能不能当恢复入口 |
|---|---|---|
| 源账本（`ContextSourceLedger`） | 本次请求里见过的完整正文 | 只在本次请求内，不跨请求 |
| `conversation_message` | 只有 user / assistant 的正文 | 工具结果不在里面 |
| `tool_call_log` | 审计用副本，结果截到 4000 字符 | 是审计，不是恢复来源；`searchContext` 不查它 |
| 落盘快照（`ToolOutputStore`） | 超长工具结果的完整文本 | 有 TTL 和单会话容量上限，会被清理 |

所以「工具结果的库里的原文还在」这句话对工具结果并不成立。真正能读回原文的只有落盘快照，入口是 `readFile` 读那条带签名的 `[artifact-ref]` 路径，**不是** `searchContext`。

工作集里的通用工具组退休（`RECOVERABLE_OLD_TOOL_GROUP`）只对**带签名快照**的工具结果生效：正文里必须有一个验签通过、且带 `sha256` 的引用；退休这一刻还必须证明**内容哈希一致**、并且（生产路径）**当前请求的沙箱允许按引用读回**。没有快照、引用验签失败、快照已被清理、内容被替换、或路径不在允许读取范围内的结果一律不退休，正文照发。

工具结果用**独立的、本次请求内的模型轮次**判断新旧，不能套用按用户回合算的 `RECENT_ROUNDS`：工具结果总是追加在本轮用户消息之后，按用户回合算的话永远落在「最近回合」里，永远不可能退休。现在的条件是同时满足：

1. 历史 + 工具结果确实超过 `soft-budget-tokens`（没有预算压力就不退休）；
2. 结果产生于至少 `TOOL_RESULT_RECENT_ROUNDS`（3）个模型轮次之前，最近三轮的结果保留；
3. 计划步骤已完成（活动步骤依赖的证据由 `PROTECTED` 留下）；
4. 正文里有验签通过、带内容哈希的快照引用，且**退休这一刻**快照可读、内容哈希一致。

轮次只是候选条件，不是唯一依据。`[ContextShadow]` 行里的 `toolResultTokensEst` / `budgetPressureTokensEst` 分别记录工具结果和「历史 + 工具结果」的估算；`reasonCounts` 会说明每条结果为什么被保留（`TOOL_RESULT_RECENT_ROUND`、`TOOL_RESULT_SNAPSHOT_MISSING`、`TOOL_RESULT_SNAPSHOT_HASH_MISMATCH`、`TOOL_RESULT_SNAPSHOT_UNAUTHORIZED`、`TOOL_RESULT_RECOVERY_PROTECTED` 等）。

退休的写法是：`tool_call` 和 `tool_result` 都留着，只把结果正文换成一行省略标记，标记里带原来的签名引用。这样配对不坏（`MessageProtocolValidator` 仍然通过），模型手里也仍有一条能 `readFile` 的路径；引用不可用时标记会直接说明读不回来，而不是给一条不存在的精确读取。整组直接删掉是错的：删掉会同时丢掉快照路径，模型就再也不知道去哪读。

## M3：快照完整性与生命周期

三处判断共用同一个校验器 `ToolSnapshotIntegrity`：退休闸门（`ContextProjectionPolicy`）、实际恢复（`FileTool.readFile`）、历史压缩（`ToolHistoryCompactor`）。顺序固定为：引用必须带 sha256 → 路径合法（非 UNC、冒号只在盘符位）→ 沙箱授权（`PathSandbox.resolveForRead`，签名不能扩大可读范围）→ 文件存在且是普通文件 → **字节的 SHA-256 与引用一致**。任何一步失败都返回具体状态，调用方拼出明确原因并保留原始正文。

- **退休时校验**：不再只看「文件存在」。内容被替换、快照被删、路径越权、引用缺哈希，都不许退休。
- **恢复时再校验**：`readFile` 每次都重新验签、验授权、验哈希，并**用同一次读取到的字节**做正文（校验与读取不分开，缩小检查后被替换的窗口）。缺哈希的旧引用一律拒绝，不返回未校验内容。
- **保留租约**：引用真的发出去之后，`ToolOutputStore.retain(path)` 给快照打一个 `DEFAULT_RETAIN_LEASE`（1 小时）的进程内租约；租约内 TTL 清理和单会话容量清理都跳过它，租约到期自动失效并惰性清理，会话删除时一起丢掉。不是永久保留，也没有持久化引用计数。
- **恢复内容保护**：`readFile` 传签名引用、或 `searchContext operation=read` 产生的结果被记为**恢复结果**（身份来自工具名 + 入参结构，不看正文措辞），在 `RECOVERY_PROTECT_ROUNDS`（6）个模型轮次内不退休。到期后预算压力、可恢复性、轮次、计划步骤、快照完整性全部重新生效。这条状态只在本次请求内，不跨请求。

**M3 边界（诚实说明）**：租约只活在进程内，重启即丢；重启后旧引用不再有任何保留保证，清理照常发生。已经发给模型的失效引用**不会**被自动撤销：快照在检查之后、模型读取之前被删掉时，读取端会明确失败（`文件不存在` / `快照内容校验不一致`），不会返回伪造正文；源账本里只有「预览 + 标记」，不是完整正文，所以也不能拿它悄悄替换回原文。需要内容时重新调用工具。这不等于操作系统级的原子文件协议。

`ToolHistoryCompactor` 在压缩时用同一套标记，同样不拆开一对工具调用和结果。没有可靠恢复路径的必要结果会留下正文，而不是只留一个打不开的指针。

曾经有过一条只针对「同一路径、同一正文、中间没有改盘」的重复 `readFile` 退休。那条路径和配置 `tool-result-retirement-enabled` 已经删除。不要把它和工作集的通用退休当成同一件事，也不要在配置里再找这个开关。

子代理房间另有自己的截断：单条工具结果默认 4000 字符，交回主代理的摘要更短。主循环的 12000 字符硬顶只在 `app.subagent.dispatch-v2=true` 时生效，默认关。

MCP 超长结果的落盘见 [MCP 与安全](MCP-AND-SECURITY.md)。那不是这一节的压缩。

## 优先留下的信息

投影和压缩尽量保留：

- 当前用户消息和仍有效的约束
- 活动计划
- 最近的工具组和仍被后续步骤依赖的证据
- 没有稳定恢复路径的错误和结论

更早的、已经有定位可以再读的旧助手回复，可以先退出本轮输入。带签名快照的旧工具结果按上一节换成一行省略标记；没有快照的正文不动。

## searchContext

`ContextAssetTool` 的 `searchContext` 是只读工具，默认允许执行，不弹审批。它只查三类：本会话消息、该用户的用户记忆、当前计划。

- 用户和会话来自会话上下文，不来自工具参数。不能用它读别的会话。
- 搜索先给短片段。`hasMore` 时用 `nextCursor` 翻页，`order=asc` 可以找更早的原文。
- 片段不够时，按结果里的 locator 再读。已经知道 `message|<id>` 时直接读，不要拿 id 当关键词。
- 单次读取有字符上限，避免一次把窗口再次填满。

它不提供工具快照的通用检索，也不能按工具调用 id 读取任何一条工具结果。要读回落盘的工具快照，只能用 `readFile` 读那条带签名的 `[artifact-ref]` 路径。这类引用走自己的校验：每次读取都重新验签、验沙箱授权、验内容哈希，过期、丢失或被改过就失败，不返回一段看起来成功的内容。没有稳定签名密钥时，进程内标记在重启后失效。磁盘上有文件，不等于引用一定可读。刚通过 `searchContext operation=read` 取回的内容，在当前请求的后续轮次里受有限的恢复保护（见上一节），不会被立刻再次退休。

## 两种记忆

| | 工作区记忆 | 用户记忆 |
|---|---|---|
| 配置 | `app.memory.enabled`，默认开 | `app.user-memory.enabled`，默认开 |
| 存在哪 | 当前工作区的 `memory/*.md` | SQLite，按用户 |
| 何时注入 | 在该工作区对话时 | 该用户的后续会话 |
| 谁来写 | `saveMemory`，以及会话结束后对索引的整理 | `saveUserMemory` / `forgetUserMemory` |
| 审批 | 按工具权限表 | 每次保存和删除都要批准，不能被会话的完全访问档跳过 |

工作区记忆有文件数和字数上限。没有 `memory` 目录时，这层是空的。

用户记忆最多 40 条。类别只有 profile、preference、constraint、project_context。提示词要求只记用户在当前轮次里明确说过、并且以后仍成立的内容。代码不另做一套来源判断；未批准不会写入。明显的私钥、口令和访问令牌会被拒绝，但不能覆盖所有秘密格式。

两条记忆都不会注入子代理房间。

## 消息配对

发给模型的工具调用必须带上对应结果，否则协议不完整，请求会被拒绝或回滚。`MessageProtocolValidator` 在压缩和退休之后检查。配对坏了就保留原文，不发出这轮。

工作集是从源账本重新投影的。改的是副本，不是先把库里的历史改坏再发送。

## 这些机制怎样一起工作

顺序是：先取库存历史。工作集开启（默认）时由 `ContextCompactor.assemble` 拼接历史，并在达到阈值时把够旧的 user/assistant 历史换成一段带覆盖范围的摘要；随后工作集从源账本投影出本轮视图（跳过已被摘要覆盖的原文）。工作集关闭时才先按预算做历史摘要（`buildMessages`），再把结果交给模型。硬窗口在每次最终模型请求前都会检查：投影后的内容仍超过窗口就停止本轮，不发送、不静默丢内容；投影本身失败时也会用原始请求再兜一次窗口检查。检索不自动发生。系统提示告诉模型：当前上下文够用就直接做；缺了旧决定或旧原话，再调用 `searchContext`。

摘要、投影和检索解决的是不同问题。摘要缩短旧对话；投影少发旧助手回复，并在满足签名快照条件时把旧工具结果换成一枚仍可 `readFile` 的省略标记；检索把一条指定旧消息找回来。三者都不跨请求保留工具结果原文。

## 局限

- 估算不是服务商账单上的 token 数。
- 摘要可能丢掉细节。丢掉的内容要靠检索或重新读文件找回来。
- 工作集减少的是发送量，不减少已经发生过的工具调用。
- 没有一份随仓库提交的、用真实模型跑完的费用对比。
- 离线测试覆盖压缩、投影、配对和 `searchContext` 的归属。这没有代替一次真实长会话。
- 历史摘要的跨请求复用只在进程内（64 个会话，LRU），重启或多实例部署时会重新摘要一次；没有持久化摘要表，也不做跨进程共享。
- 摘要质量由模型决定。代码只做结构校验（非空、长度上限、必须变短），不判断摘要是否真的保留了用户约束；约束的可靠性来自「最近 3 个用户回合原文保留 + 覆盖范围可 read 回原文」，不是来自摘要模型的自述。
